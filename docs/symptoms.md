# 症状カタログ — 「この言葉で過去の原因を引ける」ようにするための表

このファイルは**症状の言葉と、その原因を結びつける索引の入口**です。

## なぜ要るか

同じ症状を2度調べ直さないためです。実際にこのリポジトリでは、
**「ローカルは正しいのに本番だけ違う」型の不具合を1週間で3回**踏みました
（OGPが0バイト / 旧スプラッシュがCDNに残留 / チャンクに旧コードが残留）。
3回とも別々に何時間もかけて調べ直しています。

症状に短いIDを付け、`ai-hub/index.json` の `triggers` に登録しておくと、
次に同じ症状を見た人（＝多くの場合、次のセッションのAI）が
**調べ直さずに原因へ辿り着けます**。

## 使い方

1. 不具合が起きたら、下の表から**症状IDを探す**
2. 見つかったら `node ai-hub/bin/hub.mjs find --sig "<症状の実文言>"` で原因を引く
3. **表に無い症状**だったら、原因が分かった時点で
   **この表と `ai-hub/index.json` の両方に足す**（片方だけだと繋がりません）

## ★大事な原則

- **「0件だった」と「測っていない」を混ぜない。** 検査が緑でも、
  それが何を見ていないかを必ず読むこと。
- **ローカルで正しいことは、配信が正しいことの証拠にならない。**
  画像・チャンク・静的ファイルは**本番から落として実物を測る**。
- **HTTPステータスは嘘をつく。** 200 / image/png のまま中身が0バイト、が実在した。


## ★症状IDの付け方（ここを間違えると、逆に誤誘導します）

**接頭辞はリポジトリごとに分ける。** `SS-01` のような汎用の番号は使わないこと。

2026-08-23 に実際に踏みました。最初この表を `SS-01`〜`SS-06` で作ったところ、
検査が **「索引ヒット 100% / 未登録 0件」** と報告しました。
実際には1件も登録していないのに、です。

原因は **`soushin-suggest.link` が既に `SS-01`〜`SS-06` を使っていた**こと
（一覧が真っ白 / Windowsの地雷 / 配布zipに実データ混入 …と、まったく別の意味）。
番号がぶつかっただけで「登録済み」と判定されていました。

★これは緑になるので気づけません。しかも次に同じ症状を見た人は
**別プロジェクトの原因ページへ案内される**＝索引が無い状態より悪くなります。

→ このリポジトリは **`SG-`**（surechigai）を使います。

## SG-01 共有画像が真っ白になる

**症状の言葉**: 「OGPが出ない」「シェアしても画像が真っ白」「サムネイルが表示されない」

**見分け方**: `curl -sI` は 200 / image/png を返す。**サイズを見ると 0 バイト**。

**過去の原因**: Satori に `border: undefined` を渡すと描画に失敗し、空を返す。
アバターがある場合だけ値が入るので、**Xアイコンを取得できた人は正常・できない人は真っ白**
という分かりにくい壊れ方をした（2026-08-21・2日間本番で壊れていた）。

**検査**: `pnpm check:ogp`

## SG-02 起動画面が古いまま変わらない

**症状の言葉**: 「スプラッシュがおかしい」「直したのに反映されない」「起動画面が前のまま」

**見分け方**: リポジトリの画像は正しい。**本番から落とすと別物**。
`curl -sI` に `cf-cache-status: HIT` と `Age:` の大きな値が出る。

**過去の原因**: ファイル名が固定のまま中身を差し替えたため、Cloudflare が
`max-age=31536000, immutable` で旧版を配り続けた。**20解像度のうち5件だけが旧版**という
混在で、機種によって見え方が違うので気づけなかった（2026-08-22・35時間）。
デプロイの自動パージは `Cloudflare secrets not set` で一度も動いていなかった。

**検査**: `pnpm check:splash-served`

**★2026-10-05 追記**: 起動画像を内容ハッシュ名（`ios-<w>x<h>.<sha256先頭12桁>.png`）にし、`?v=` を廃止した。
固定名＋クエリは SG-02 と同じ型の罠だった（クエリを CDN・ブラウザ・iOS がどう扱うかに依存する）。
画像の中身が変われば名前が変わるので、旧版が配られ続ける余地が無い。作り直したら `pnpm brand:icons` → `pnpm splash:sync`。

**★2026-09-14 追記: 同じ言葉で訴えられたが、原因が別だった例**

「スプラッシュがおかしい」と言われて5経路すべて実測したところ、**起動画面そのものは無罪**だった
（検査2本合格／起動画像21件とアイコン4件が全て `200 image/png`／`background_color` 無し（当時。2026-10-05 に戻した）／
`boot-mark.png` 実在／ブートベールも無条件 `useEffect` で2フレーム後に解除される健全な実装）。

**真因は `public/manifest.json` の `short_name` が28文字になっていたこと**。
iOS のホーム画面アイコン名は12文字程度で切られるので、途中で途切れて見える。
★`PWA_APP_NAME`（`components/brand/web-document-head.tsx`）を直しても
**manifest は追随しない**（別ファイル・手書き）。ブランドコピーを変えたら必ず両方見る。

**★bpp の開きを数字だけで読まない**
`check:splash-served` は最大÷最小が2.5倍を超えると赤にするが、**並びの形も見ること**:
- 旧版混在（2026-08-22 の実障害）＝ 0.279 と 0.619 が**飛び飛びに混在**
- 正常 ＝ 解像度と**単調に相関**（小さい画像ほど bpp が高い。PNG の圧縮効率の差）

2026-09-14 の実測は1.98倍だったが完全に単調で、混在ではなかった。

## SG-03 ボタンを押しても何も起きない

**症状の言葉**: 「押しても反応しない」「ログインできない」「Buttons were unresponsive」

**見分け方**: ボタンは正しく描画され、押せる見た目になっている。
**押してもブラウザが開かず、エラーも出ない**。コンソールにも何も出ない。

**過去の原因**: Clerk 未ロード時に `startOAuthFlow` が**例外を投げず**
`createdSessionId: ""` を返す。呼び出し側の `if` を素通りし、`try` が正常終了するので
`catch` の Alert も出ない。さらに `isAuthReadyForUI` は1000msで**無条件に** true になるため、
ボタンは「押せる見た目」に戻る（2026-08-22・iOS build 520/521 が却下）。

**★注意**: `disabled` にする方向で直さないこと。読み込みに失敗すると
**永久に押せなくなり、却下より悪化する**。

## SG-04 共有ボタンが無反応（特定の共有先だけ）

**症状の言葉**: 「Threadsに共有できない」「押しても何も起きない」

**見分け方**: URLは正しく組み立てられている。**特定の共有先だけ**動かない。

**過去の原因**: `openExternalUrl` は許可リストに無いドメインで**無言で false** を返す。
`threads.com` が一度も許可リストに入っていなかった（2026-08-21）。
共有まわりのテストは60件あったが、**組み立てたURLが実際に開けるか**は見ていなかった。

**★注意**: 許可リストの検査を grep で書くと、リストから外しても緑のままになる。
**戻り値で照合する**こと。

## SG-05 検査が緑なのに不具合が続く

**症状の言葉**: 「テストは通っているのに直らない」「ゲートが緑なのにおかしい」

**見分け方**: 検査の出力に**走査件数が出ていない**。または「0件」で緑になっている。

**過去の原因**: 走査対象が0ファイルでも `exit 0` で「OK」と表示していた
＝**何も測っていないのに合格**（2026-08-22）。
また `check-native-unsafe-dom` は `pnpm check` にも CI にも未登録で、
**誰にも実行されていなかった**（2026-08-21・iOS 518 却下の検出役だったのに）。

**★注意**: 「0件だから緑」は「一度も測っていない」と区別が付かない。
合格には**走査件数という根拠**を要求すること。

**検査**: `pnpm check:instruments`（毒→赤を機械で確認）

## SG-06 修正が本番に反映されない

**症状の言葉**: 「デプロイしたのに変わらない」「version.json は一致しているのに古い」

**見分け方**: `version.json` の `commitSha` は新しい。**なのに挙動が古い**。

**過去の原因**: Metro は子チャンクの参照先URLを親チャンクのファイル名ハッシュに含めないため、
CDN の immutable キャッシュに「同名・別内容」の親チャンクが残ると旧コードが配信され続ける
（2026-07-04）。

**対処**: `theme/tokens/index.ts` の `CDN_CACHE_EPOCH` を +1 してデプロイ（全チャンク強制改名）。

**★注意**: `version.json` の一致は**デプロイの証明にならない**。

## SG-08 「Loading module …」で止まり、再試行を押しても直らない

**症状の言葉**: 「Loading module https://…/_expo/static/js/web/sign-in-….js」
「再試行を押しても直らない」「アプリが開かない」「白い画面に赤い文字」

**見分け方**: 実在するチャンクは正常に配信されている（`200 application/javascript`）。
**存在しない名前**を叩いたときだけおかしい。★`curl -I` では 200 が返るので「正常」に見える。

```bash
curl -sS -o /dev/null -w "%{http_code} %{content_type} %{size_download}B
"   https://surechigai.kimito.link/_expo/static/js/web/NOPE.js
```
→ **404 以外なら赤**。200 でトップページ（67708B前後）が返っていたのが2026-09-06の障害。

**過去の原因**: `dist/404.html` が無く、Vercel がどのルートにも当たらないパスへ
トップページの HTML を **HTTP 200** で返していた。ブラウザは HTML を ES module として
実行できず「Loading module failed」になる。さらに `Cache-Control: immutable` が付くため
**リロードしても1年間直らない**。

**★現状（2026-09-06）**: 200 が返る問題は**まだ直っていない**。
`routes` の `handle:filesystem` + `status:404` で直せるが、
★**routes を足すと `headers` が丸ごと無効化され、CSP を含むセキュリティヘッダーが
本番から全部消える**（公式ドキュメントは「併用できる」と書いているが実挙動は違う）。
セキュリティを優先して撤回した。

代わりに **1年キャッシュだけを断った**（`immutable` を実在ファイル名の形
`:hash([0-9a-f]{32})` に絞る）。これで「押しても直らない」→「**リロードすれば直る**」になる。
`pnpm check:missing-404` は今も赤で、これは「直っていない」を正しく報告している状態。
★緑にするために検査を弱めないこと。

**★診断を外しやすい点（実際に2回外した）**:
- 「rewrite の負先読みが効いていない」→ **誤り**。負先読みは正しく動く（公式推奨形）。
  除外された結果「行き先が無い」状態になり SPA 既定挙動に落ちるのが真相。
- `404.html` を置いても効かないことがある。★返るHTMLの**サイズを比べる**まで
  「404ページ」と「トップページ」を区別できない（どちらも `text/html` 200）。

**★注意**: `headers` はファイルの実在を問わずパスパターンで当たる。
拡張子ベースの広域 `immutable`（`/(.*).js` 等）は、壊れた応答に1年キャッシュを付ける。

**検査**: `pnpm check:missing-404`

## SG-07 静かなのに壊れている（心拍が無い）

**症状の言葉**: 「エラーは出ていないのに動いていない」「ログに何も残っていない」

**見分け方**: ログが**空**。しかしそれが
- A. 本当に何も起きなかった
- B. ★計器そのものが動いていなかった（起動直後に落ちた等）

の**どちらかを区別できない**。★沈黙は正常の証拠にならない。

**現状**: ★このアプリには**心拍がありません**（2026-08-27 実測・`pnpm check:heartbeat` が exit 1）。
症状が出たときだけログを書くので、上の A と B が同じ見た目になります。

**★なぜ今すぐ直さないか**: 心拍を入れるのは製品側の設計判断（何を・どの間隔で・どこへ書くか）で、
機械的に足せるものではありません。★「緑にするために検査を弱める」ことはせず、
**無いものは無い**と記録しています。

**★検査を `pnpm check` に入れていない理由**: 今入れると毎回赤になり、
赤が日常になって本物の赤を見なくなるためです。手で叩けます:

```
pnpm check:heartbeat
```

心拍を実装したら `scripts/diagnostics/run.mjs` に登録してください
（登録を忘れても `check-gates-are-wired` が孤児として拾います）。

## SG-09 起動のときに画面がちかちかする

**症状の言葉**: 「スプラッシュがちかちか」「起動画面が点滅する」「開くと色が何回も変わる」

**見分け方**: ホーム画面から開いた(PWA)直後の約1秒に、色の違う画面が連続する。
目視では何が何ミリ秒続くか分からないので、**画面録画をフレームで割る**か、下の測定を使う。

**2026-10-05 の実測（iPhone の実機録画 120fps ／ Android 実機の録画 ／ Playwright で本番を測定）**:

| 段階 | iPhone | Android |
|---|---|---|
| 1 | 黒（OSがアプリを開く演出。こちらでは触れない） | 白＋アイコン（OS標準。この時点の `manifest` に `background_color` が無かったため白。2026-10-05 に #E2EDF7 を戻した） |
| 2 | 自作のベール（ロゴ＋タイトル）が約0.08秒 | 自作のベール（アイコンの大きさ・位置が飛ぶ） |
| 3 | **空白 → 灰色の骨組み → 本編** | **空白（約0.1〜0.15秒）→ 本編** |

- 段階3が**アプリ側の原因**: ルートのレイアウトがマウントした時点でベールを外していたが、
  タブの画面はまだ読み込み中だった。解除から本編まで、ゲストで約350ms / ログイン済みヒントで約570ms
  （CPUの速さによらず再現）。
- 直した所: ① 灰色の骨組み(`ChunkFallback`)を、ベールと揃えてある `BrandLoadingScreen` に寄せた
  （トップ `app/(tabs)/index.tsx`、タブ全体の待機 `TabAuthenticatedShell`、events/map/mypage/zukan の認証待ち）。
  画面の一部の小さな待機（`lazy-heavy-components` 等）は全画面にしないので `ChunkFallback` のまま。
  ② ベールの解除を、ルートのレイアウトではなくトップ画面の中身のマウント後に移した（`lib/boot-veil.ts`）。
  どちらも**新しい仕組みは足していない**（既存部品の使い回しと、呼び出し場所の移動だけ）。
- ★直せていない所（理由つき）:
  - iPhone の標準の起動画像（`apple-touch-startup-image`）が出ない件。iOS は**ホーム画面に追加した時点で
    起動画像を固定**するため、追加し直さないと反映されない。配信は正常（`check:splash-served` 合格）。
  - ★2026-10-05 訂正: 以前ここに「`manifest.background_color` を足すと iOS 16.4+ が起動画像を無視するので
    足せない（Android の白い起動画面はトレードオフ）」と書いていたが、**この説には Apple/WebKit の公式記述という
    一次情報が無く**、リポ内の根拠も kimito.link の実機観察1件（OS 版の記載なし）と静的検査だけだった。
    同日の iPhone 実機録画では、`background_color` を外した状態でも起動の最初が黒で起動画像は出なかった
    ＝ この説では現実を説明できない。一方 Android(WebAPK) は `name` + `background_color` + `icons` から
    起動画面を作る（web.dev）ため、無いと白でベール(#E2EDF7)との間で色が飛ぶ。
    よって `background_color: #E2EDF7`（ベール・本体の地色と同じ）を戻した。Android は地色がそろう見込み
    （マージ後に Android 実機で WebAPK を入れ直して録画確認する）。`scripts/check-pwa-splash.mjs` は
    「あり、かつ #E2EDF7 と一致」を合格条件に反転済み。
    iOS で起動画像が出ない原因は**未確定**。候補は「ホーム画面に追加した時点で固定される」
    「href の `?v=2`」「iOS 26 の挙動」。
    （2）の `?v=2` は**対処済み**（2026-10-05、起動画像を内容ハッシュ名にしてクエリを廃止。効果は iPhone で未検証）。
  - 認証済みで開いたときの待機画面は、契約テストでの確認のみ（ログイン済みの本番セッションが無く、実測していない）。

**2026-10-12 Android 実機の追加実測と修正**（moto g64y 5G／Android 15／WebAPK。`adb screenrecord` ＋ ffmpeg、
アイコンの外接矩形をフレームごとに測定）:

- **アイコンの飛び**: OS の起動画面のアイコンは幅55.4%・縦中心49.9%。ベールは幅44%・縦中心約45%
  （タイトル+スピナーと一緒に中央寄せで上へ押し上がっていた）で、切り替わりで飛んでいた。
  → `app/+html.tsx` のベールでアイコンを absolute で画面中央に固定し、大きさを `clamp(160px,55vw,260px)` に
  （66f4f7d01）。修正後は OS → ベールで上端 900px → 902px。
- **ベール解除直後の別の絵**: ベールのあとに「アイコン無しの文字だけ → ロゴ＋ゆっくりりんく（ベールと別の絵）」
  が挟まっていた（`BrandLoadingScreen`）。→ Web のフルスクリーン待機だけ、ベールと同じ `/boot-mark.png`・
  同じ大きさ・同じ中央位置に（5c4ce13ec、`__tests__/brand-loading-matches-veil.test.ts` で式の一致を固定）。
  実機3回の起動録画でアイコンが消えるコマは無く、本番ページでの再現でも待機画面のマークは 226px・画面中央。
- **起動画面の値の正本**: 地色・マークの絵・大きさ・間隔・タイトルは `theme/tokens/boot.ts` の `BOOT` に1か所だけ
  置き、ベール（`app/+html.tsx`）と待機画面（`BrandLoadingScreen`）は必ずここから取る（直書き禁止。
  `__tests__/boot-single-source.test.ts` が固定）。`manifest.json` / `package.json` / `app.config.ts` は
  ここから取れない静的ファイルなので、値が `BOOT` と同じことをテストで照合する。
  ★`app.config.ts` から `BOOT` を import してはいけない（Expo の設定読み込みが出力なしで失敗する。2026-10-12 確認）。
  OS の起動画面に合わせたマークの大きさ（`BOOT.markSize`）は実機の実測値なので、変えるときは実機で測り直す。
- **実機の起動録画を機械で判定する**: `pnpm qa:android-launch`（`scripts/qa/check-android-launch.mjs`）。
  端末を USB 接続し、PWA を「ホーム画面に追加」した状態で実行すると、Chrome を止めて3回コールドスタート →
  `screenrecord` → ffmpeg でフレームに割り、OS の起動画面のアイコン（基準）に対して、ベール〜待機画面のアイコンの
  大きさ・縦中心が飛んでいないか、消えたコマが 100ms を超えていないかを判定する（0=合格/1=赤/2=測れなかった）。
  `--runs 5` で回数、`--video a.mp4` で既存の録画を判定（実機不要）。判定ロジックは `scripts/lib/launch-frames.mjs`
  （合成フレームの単体テスト `__tests__/launch-frames.test.ts` あり）。実機が要るので CI・`pnpm check` には載せていない。
  **実行するタイミング**: 起動画面（`BOOT`・ベール・待機画面・manifest）を触ったあと／新しい機種や OS／数か月ごと。
