## 3. 起動クラッシュの真因（最重要・二度と踏まないために）

**`h3-js` がモジュール読込時に `new TextDecoder("utf-16le")` を実行する**
（`node_modules/h3-js/dist/h3-js.js:368`）。Hermes は **utf-8 しか受け付けない**ため
`RangeError: Unknown encoding: utf-16le` を投げ、誰も catch せず `abort()`。
h3-js はすれ違い判定の中核で起動時に必ず読まれる＝**100%落ちる**。

- **iPad 固有ではない**。iPhone 17 Pro でも同じく落ちることをシミュレータで確認済み
  （審査がたまたま iPad だっただけ）。
- **Web は落ちない**。標準 TextDecoder が utf-16le を持つため。
  ＝「Webは動くのにアプリだけ起動しない」の説明がこれ。

**修正**: `lib/polyfills/text-decoder-utf16.ts` を **`index.js`（expo-router より前）** で適用。

> ⚠️ `app/_layout.tsx` の先頭では**間に合わない**。expo-router は起動時に
> `getRoutes()` で app/ 配下を全部 require するため、_layout より先に別のルートが
> h3-js を引き込む。実測で **iPad は通ったが iPhone は落ちた**（＝読み込み順に依存する
> 不安定な直り方だった）。そのため `package.json` の `main` を `index.js` に変更した。

### 否定した仮説（もっともらしいが誤り。同じ道を辿らないこと）

1. 「`supportsTablet: false` が効いていない」→ **誤り**。IPA の `UIDeviceFamily` は `[1]`。
   iPhone 専用アプリを iPad の**互換モード**で起動するのは Apple の正常な審査手順。
2. 「JS バンドルが HBC 化されていない」→ **誤り**。先頭8バイトは `c61fbc03c103191f`。
3. 「babel の import-meta プラグインが worklet を壊している」→ **誤り**。実測で出力は同一。
4. 「GoogleSignIn の `GIDClientID` 不在」→ **誤り**。Clerk のプラグインは env 無しなら no-op。
5. 「`expo-dev-client` が dependencies にある」→ 実在の問題だったが**クラッシュの原因ではなかった**
   （前セッションで修正済み。それでも 499 は落ちた）。

**教訓: 静的にコードを読むだけでは当たらなかった。シミュレータで実際に起動させたのが唯一の決め手。**

## 5. 自作プローブが「偽の緑」を3回出した（最重要の教訓）

`.github/workflows/ios-crash-probe.yml` を作って実機起動を確認したが、
**判定を自作した結果、自分で偽陽性を作り込んだ**。

| 回 | 症状 | 原因 |
|---|---|---|
| #4 | 60分でタイムアウト cancelled | `simctl launch --console-pty` は**アプリが終了するまで返らない**。<br>クラッシュする版では完走し、**直った版だけ詰まる**罠 |
| #6 | 両デバイス `VERDICT: OK`（**嘘**） | **macOS に GNU `timeout` が無い**(rc=127)。アプリを一度も起動せず<br>ログが空になり、それを「OK(痕跡なし)」と報告していた |

## 7. 追加した新機能: 写真から思い出をとりこむ

設計は `docs/photo-import-and-viral-DESIGN.md`（会議4体→Fable設計→司令塔が裏取り）。

**写真は端末から一切出さない。** EXIF の座標と撮影時刻だけを読んで、過去日付の足あと
（`visibility: "private"`）にし、図鑑（visitedAreas）を埋める。画像ストレージ不要・
UGCモデレーション義務なし・EXIF公開事故なし。

- 入口: `/photo-import`（本番で HTTP 200 確認済み）
- 依存追加は `exifr` 1個だけ（依存ゼロの純JS＝autolinking 対象外で権限申告は増えない）
- **EXIF が取れない写真は手動指定に合流**（日付・緯度経度）。実ブラウザで
  「0枚 → 日付入力で1枚 → 座標入力で2枚」と増えることを確認済み。
  ここが会議の批判役が刺した穴（EXIF依存にすると何も起きないアプリになる）への回答
- **すれ違いマッチングは実行しない**（過去日付の在圏を遡ると意味論が壊れ、
  他人の写真で偽の在圏を作れてしまうため）

### 実ブラウザ検証で潰した不具合3件（静的には分からなかった）

1. `useToast must be used within a ToastProvider` → 依存をやめて画面内にエラー表示
2. `Unable to find tRPC Context` → `useTrpcReady()` で本体をマウントしない型に
   （`enabled:false` では防げない。`nav-live-prefecture-panel` と同じ）
3. ゲストが無限スピナーでログイン導線に到達できない → ガードの順序を修正

## 8. OGP が「出たり出なかったり」した真因

**タイミング一点。** シェア押下時に `setWarmImageUrl()` で state を更新し、**次のレンダリング**で
温める作りだったため、ウォームが始まる前に X を開いていた。生成は 1.6〜2.9 秒かかる。

本番実測:
| | 結果 |
|---|---|
| 未ウォームでクローラー到着 | `x-vercel-cache: MISS` / 2.0秒（Xは~3秒で諦める） |
| ウォーム完了後に到着 | **HIT / 0.19秒** |

対策: `warmOgImageNow()` をシェア直前に `await`（上限3.2秒で必ず打ち切るのでシェアは止まらない）。

> なお `lib/ogp/warm-og-image.ts` は**どこからも呼ばれていないデッドコード**。
> 実際に効いているのはブラウザ側の `hooks/use-warm-og-image.ts`。
