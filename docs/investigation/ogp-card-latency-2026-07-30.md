# OGPカードが「出るときと出ないときがある／遅い」— 実測と対策（2026-07-30）

## 発端

ユーザーからXの実投稿スクショ2件（諏訪市・岡谷市）で「OGPが出るのが遅いときがあるかも」
「でるときとでないときがある？」と報告。両方とも**カードは出ているが画像が欠落**し、
左側が灰色プレースホルダのテキストのみカードになっていた。

## 実測（本番 surechigai.kimito.link に対して curl）

### メタHTML自体は正常

```
curl -A "Twitterbot/1.0" https://surechigai.kimito.link/u/TGszTcz7stEb
```

`og:title` = 「@streamerfunch は 岡谷市 にいるよ｜…」、`og:image` = 座標入りの `/api/og?...`、
`twitter:card` = `summary_large_image` がすべて正しく出力されていた。**メタは無罪**。

### 画像生成が常時5〜6秒かかっている

| 条件 | 所要 |
|---|---|
| キャッシュミス（座標あり・StaticMap） | 5.05〜8.31秒 |
| キャッシュミス（座標なし・夜景72星+SVG） | 5.49〜5.60秒 |
| キャッシュミス（文字最小・背景なし） | 4.94秒 |
| 連続4回（同一インスタンスに別URL） | 7.30 / 5.83 / 5.86 / 5.77秒 |
| 並列4本 | 5.60 / 8.18 / 8.44 / 10.90秒 |
| **キャッシュヒット（同一URL2回目）** | **0.17秒** |

### 主因の切り分け

- **コールドスタートではない** — 連続で叩いても毎回5.8秒前後。
- **外部取得は主因ではない** — Google Fonts CSS 0.12秒 / `japan.svg` 0.09秒。
- **描画内容を変えてもほぼ一定**（5.0〜5.6秒）＝ `ImageResponse`（satori→PNGラスタライズ）
  そのもののコスト。
- 並列で悪化するので、同時シェアが重なるとさらに不利。

### なぜ「出るときと出ないときがある」のか

X のクローラーは **~2秒**で諦める（`api/og.tsx` のコメントにも既記載）。したがって:

- 誰かが先にそのURLを踏んでいれば **0.17秒**で返る → 画像が出る
- 冷たいキャッシュだと **5〜6秒** → Xが待たず、画像なしカードになる

さらにシェアURLには `v=<記録時刻>` が付く（`buildPublicSharePageUrl`）。
**新しいチェックインほど必ず新しいURL＝必ずキャッシュミス**になるため、
「新しくシェアした時ほど画像が出ない」という体感になっていた。

## 対策（実装済み・fe36b8c1f）

キャッシュを**先に温める**方式を採用。生成自体の5秒は削れないため、
クローラーが来るより前に生成を終わらせる。

1. `encounter.checkIn`（`modules/encounter/api/encounter.ts`）
   位置保存直後に投げっぱなしでウォーム。後続のマッチング処理（数秒）の裏で生成が進む。
2. `ogp.getOrCreateShareSlug`（`server/routers/ogp.ts`）
   シェアリンク発行時にもウォーム。**応答は待たせない**。

### 実装上の判断

- **応答を待たない**: ウォーム完了を `await` するとシェアボタンの応答が5秒遅くなる。
  この導線は `prepareSharePopup()` でクリック直後に空白ポップアップを確保してから
  非同期処理をする設計（過去のポップアップブロック地雷対策）のため、待つと
  ユーザーが空白タブを5秒見ることになる。よって `void` で投げっぱなしにした。
- **URL組み立てを `buildWarmTargetUrl` に集約**（`lib/ogp/warm-og-image.ts`）:
  シェア時にクローラーが実際に取りに来るURLと1文字でも違うと別キャッシュキーになり、
  ウォームが完全に無駄になる。`ogpContext: true` の解決条件もシェア側と揃えている。
- **全て best-effort**: ウォームの失敗はチェックインもシェアも止めない。

## 残る限界と、次にやるなら

- チェックイン直後にシェアされた場合、ウォームが5秒で終わる前に投稿が完了すると
  依然として間に合わない可能性がある（実用上は文章を書く時間があるので多くは救われる）。
- 根本的に潰すなら **生成自体を軽くする**方向:
  - `ImageResponse`（satori）をやめ、事前生成PNG＋軽量な合成に寄せる
  - 県単位など粗い粒度の静的画像に寄せる（ただし「その場所の地図が出る」価値は落ちる）
- Vercel の `waitUntil`（`@vercel/functions`、現在未導入）を入れれば、レスポンス後も
  ウォームを確実に完走させられる。投げっぱなしの確実性を上げたい場合の選択肢。
