## A. 結論

**初回提出には課金を入れない。現行の「完全無料」申告のまま初回審査を通し、課金は v1.1 で「月額サブスクリプション1本（RevenueCat 経由のネイティブIAP、広告非表示＋データエクスポートの2機能から開始）」として入れる。**

根拠:
1. SIWA未実装（Guideline 4.8）という確定ブロッカーが残る状態で、IAP審査（3.1.2 のメタデータ要件・サンドボックス購入の実機審査・規約整合チェック）という却下ベクタを重ねるのは審査変数の純増でしかない。
2. 現状は決済ライブラリゼロ・プレミアム4機能の実装ゼロ・広告在庫すら自社カード1枚で、**売るものがまだ存在しない**。
3. `app.config.json` の `businessModel` 3フラグ・`app/terms.tsx` §8・`app/privacy.tsx` §4 は現状「無料」で三点一致しており、初回はこのまま出すのが最も矛盾がない。v1.1 での追加は「既にストアに存在するアプリへのIAP追加」となり、初回一発審査より遥かに低リスク。

## B. 理想の体験フロー

### B-1. 原則: プレミアムは「売り込まれるもの」ではなく「見つけるもの」

商業訴求は訴求密度ルール（`docs/uxux-stability-audit-SPEC.md` §2.2: 1画面1商業訴求・スタック順序固定・シェアより下）で厳しく縛られている。プレミアムCTAのために新しい訴求枠を作らない。導線は3つだけ。

### B-2. 導線1: 既存の協賛カード配信に「お知らせカード」として相乗り（地雷Jの解）

プレミアム紹介カードは、**新規UIを一切作らず `sponsor_cards` に `isSelfPromo: true` の行として投入**する（`linkUrl` は `/premium`）。

- `ads.getCards` は**1枠につき1枚しか返さない**（`ads.ts:239` の `pickWeighted`）。プレミアムカードと協賛カードは同じ抽選プールに入るため、**同一画面に両方出ることが構造的に不可能**。1画面1商業訴求ルールがコードレベルで自動的に守られる。
- 露出バランスは既存の `weight` カラムで調整（運用はSQL1行）。
- 新規ユーザー保護（7日 or 10チェックイン未満は広告ゼロ）がプレミアム訴求にも自動適用される。**習慣がつく前のユーザーに課金を見せない**のは訴求として正しく、追加実装ゼロで手に入る。
- ラベルは既存の出し分け（`ads.ts:58-61`）どおり「お知らせ」。景表法上も正確。

### B-3. 導線2: マイページ設定リストの静かな1行（常設・非カード型）

マイページの設定ブロックに「プレミアム」の行を1つ追加（歯車項目と同格の地味な行。バッジ・色・アニメーションなし）。加入済みなら「プレミアム ─ 有効（次回更新日）」の管理行に変わる。カード型訴求ではなく機能の置き場所。マイページの `mypage_stats` スロットは**プレミアム行が存在する限り無効のまま**とし、同一画面での商業訴求の重複を運用ルールとして固定する。

### B-4. 導線3: 機能ゲートに触れた瞬間の文脈的案内

プレミアム機能のUI（エクスポートボタン等）は**隠さず、無料ユーザーにも見せる**。タップすると `/premium` へ遷移し「この機能はプレミアムで使えます」と1行で示す。ユーザー起点の遷移であり訴求密度ルールの「訴求」にはカウントしない。ダークパターン（偽の進捗・煽りカウントダウン・解約妨害）は全面禁止。

### B-5. `/premium` 画面（ペイウォール兼管理画面）

`app/premium.tsx`（認証ゲート必須。ゲストにはログイン誘導）。構成は上から:
1. 特典4つの平文リスト（ENTITLEMENTS.md の言い換え。**「記録と再訪はずっと無料です」を先に明記** — 無料の鉄則を売り文句の土台にする）
2. 価格と購入ボタン
3. 「購入を復元」ボタン（Apple 必須）
4. 解約方法の説明と規約・プライバシーポリシーへのリンク（3.1.2 必須）

プラン名は詩的命名でもよいが、**価格・解約・自動更新の法的説明文は平文で書く**（「法的ラベルに詩を混ぜない」原則の準用）。

## C. 決済手段の比較と決定

### C-1. 前提の確定: プレミアム4機能はすべてIAP必須

広告非表示・高度統計・GPX/GeoJSONエクスポート・マーカーカスタマイズは、4つとも「アプリ内で消費されるデジタル機能のアンロック」であり、Guideline 3.1.1 に正面から該当する。会議で出た「実体的サービスの例外」（リアルイベント参加権等）は**この4機能のどれにも適用余地がない**。

エクスポートは「自分のデータを持ち出す権利だから実体では」と強弁したくなるが、アプリ内ボタンでアンロックされる機能である以上、審査員の目には通常のデジタルアンロックにしか見えない。米国の反ステアリング判決や日本のスマホ新法による外部決済の門は開きつつあるが、**個人開発の初回IAPで規制の最前線に立つ理由がゼロ**。

手数料は Small Business Program（年間収益 $100万未満、要申請）で **15%**。月額400円なら手取り約340円。Railway の DB 費用は加入者数人でペイし、RevenueCat は月間トラッキング収益 $2.5k まで無料。本アプリの課金は黒字化装置ではなく「サーバー代の自弁＋広告非表示の受け皿」であり、この規模感で15%と30%の差は生死を分けない。

### C-2. 比較表

| 観点 | RevenueCat | react-native-iap 素実装 | Clerk Billing |
|---|---|---|---|
| iOS 3.1.1 適合 | ○ ネイティブIAP | ○ ネイティブIAP | **× Stripe=外部決済。iOSアプリ内で使えば即却下** |
| レシート検証 | ○ サーバー側で代行 | × 自作（鍵管理・更新イベント処理） | − |
| サブスク状態同期 | ○ Webhook 1本 | × 更新/失効/返金/猶予を自前 | − |
| iOS/Android 両対応 | ○ 単一API | △ 分岐多い | − |
| 費用 | $2.5k MTR/月まで無料 | 無料 | Stripe手数料+Clerk課金 |
| 姉妹サービスへの影響 | **なし**（Clerkと独立） | なし | **あり**（`clerk.kimito.link` 共有・影響範囲が検証不能） |
| 運用負荷 | 低 | 高 | − |

### C-3. 決定

**RevenueCat（react-native-purchases + Expo config plugin, EAS Build 前提）に1本化。**
Clerk Billing は「iOS 3.1.1 不適合」と「インスタンス共有」の2点で恒久的に除外。react-native-iap 素実装はレシート検証と更新イベント処理の自作が個人開発の運用に見合わず却下。

商品構成は**月額サブスクリプション1本のみ**（月額400円目安）。商品を1つに絞るのは、ストアの商品管理・審査メタデータ・復元処理がすべて商品数に比例して増えるため。

**Webでの購入は v1.1 では提供しない。** プレミアム状態はサーバー正本なので、ネイティブで購入すればWeb版にも即反映される。Web の `/premium` は状態表示＋「購入はアプリから」の案内のみ（逆方向 — iOSアプリからWeb決済への誘導 — が3.1.1違反なのであって、WebからアプリへのIAP案内は問題ない）。

## D. 具体機構

### D-1. スキーマ: `drizzle/schema/premium.ts`（新規）

```
premium_entitlements
  id            serial PK
  userId        integer NOT NULL UNIQUE          -- users.id
  status        text NOT NULL DEFAULT 'active'   -- active / expired / revoked
  productId     varchar(64) NOT NULL
  platform      text NOT NULL                    -- ios / android / web
  rcAppUserId   varchar(64) NOT NULL             -- "user_" + users.id
  currentPeriodEnd  timestamp NOT NULL
  willRenew     boolean NOT NULL DEFAULT true
  createdAt / updatedAt  timestamp
  INDEX: userId(unique) / currentPeriodEnd
```

`drizzle/schema/index.ts` へのエクスポート必須（ディレクティブ1）。

**地雷Cを踏まないフラグ設計（最重要）**: `sponsor_config` の事故は「行が無いときのフォールバックが `enabled: true`（フェイルオープン）」に起因する。プレミアム判定は**逆極性**で設計する。

> **isPremium = 「`premium_entitlements` に行があり、かつ `status='active'` かつ `currentPeriodEnd > now()`」。行が無い・DBに繋がらない・判定に失敗した場合はすべて「無料」。**

- シングルトン設定行を**作らない**。ユーザー行の有無だけが真実。行が無い＝無料はマイグレーション忘れでも安全側に倒れる（誤って全員無料になることはあっても、誤って全員プレミアムになることはない）。
- プレミアムの「キルスイッチ」もDB設定行で持たない。販売停止は RevenueCat のオファリング取り下げで行う。設定行ゼロ＝地雷Cの再生産経路ゼロ。
- 広告側の既存地雷Cそのものも本実装と同時に撤去する（→ H-C）。

### D-2. Webhook: `api/revenuecat-webhook.ts`（新規 Vercel Function）

- 共有シークレットを `Authorization` ヘッダで照合（不一致は401・fail-closed）。
- `INITIAL_PURCHASE` / `RENEWAL` / `UNCANCELLATION` → upsert（`currentPeriodEnd` 更新・`status='active'`）
- `EXPIRATION` → `status='expired'`
- `CANCELLATION` → `willRenew=false` のみ（期間満了までは有効）
- 返金・不正 → `status='revoked'`
- upsert キーは `rcAppUserId`。購入時にクライアントから `Purchases.logIn("user_" + users.id)` で必ず紐付ける（匿名IDのまま購入させない）。
- 冪等: upsert なので自然に冪等。イベントログテーブルは**作らない**（`ad_stats_daily` と同じ「行を増やさない」思想）。

### D-3. tRPC: `server/routers/premium.ts`（新規・`server/routers/index.ts` に登録）

| プロシージャ | 種別 | 内容 |
|---|---|---|
| `premium.status` | protectedProcedure query | `{ isPremium, currentPeriodEnd, willRenew, platform }`。判定は `server/premium/entitlement.ts` の `isUserPremium(db, userId)` に一元化 |
| `premium.exportTrail` | protectedProcedure mutation | `{ format: 'gpx' \| 'geojson' }` → 自分の `locations` 全行（`deletedAt` null）を返す。**冒頭で `isUserPremium` チェック、非加入は `FORBIDDEN`** |

広告非表示は新プロシージャ不要。`ads.getCards` の config チェック直後に1ブロック追加するだけ:

```ts
// ads.ts getCards 内、shouldProtectUser の直前に追加
if (await isUserPremium(db, ctx.user.id)) {
  return { cards: [], dailyCap, remainingToday: 0 };
}
```

クライアント側の変更ゼロで、既存の全スロットが一括で広告ゼロになる。

### D-4. `lib/premium-features.ts`（新規 — 地雷Hの解消）

`docs/ENTITLEMENTS.md` の表をコードに写した**クライアント側の単一正本**。責務は3つだけ:

1. `PREMIUM_FEATURES` 定数: `'adFree' | 'advancedStats' | 'export' | 'markerCustom'` の機能キーと表示名・説明文
2. `useIsPremium()` フック: `trpc.premium.status` を包み、ローディング中・エラー時・未認証時は **必ず `false`**（フェイルクローズ。`TrpcReady` デフォルトtrue地雷の教訓により tRPC未準備時も false）
3. `canUseFeature(feature, isPremium)` 純関数: 将来の機能別解放の差し込み口

責務に**含めない**もの: 購入処理（`/premium` 画面ローカル）、サーバー判定（`server/premium/entitlement.ts` が正）、価格情報（ストアAPIから取得、ハードコード禁止）。

| `app/premium.tsx`（新規） | B-5 のペイウォール兼管理画面。購入ボタンは `Platform.OS !== 'web'` のときだけ発火 |

## E. MVP（v1.1 / 1〜2週間）

### E-1. 範囲: プレミアム4機能のうち「広告非表示」＋「データエクスポート」の2つ

| 順序 | 項目 | 理由 |
|---|---|---|
| 1 | 決済基盤（D-1〜D-4 + RevenueCat/ストア商品設定） | すべての前提。実装量の過半 |
| 2 | **広告非表示** | サーバー1ブロックで完成する最安の機能 |
| 3 | **データエクスポート（GPX/GeoJSON）** | サーバー側の文字列生成＋ボタン1個で完結。「正確な座標を永続保存する」という核と最も響き合う。**かつ審査員に見せられる** |
| 後回し | 高度統計ダッシュボード | 新規クエリ＋新規画面のデザイン工数が大きい。P2 |
| 後回し | 足あとマーカーカスタマイズ | 地図描画に触る＝DESIGN.md の地図原則と要調整。P2 |

**エクスポートを2番目に置く決定的な理由**: 新規ユーザー保護により、**審査員のアカウントには広告がそもそも一切表示されない**（登録7日未満・チェックイン10件未満 → `ads.ts:89-106`）。「広告非表示」だけを売って審査に出すと、審査員には**購入前後で何も変わらないアプリ**に見え、Guideline 2.1（機能しないIAP）の却下ベクタになる。エクスポートは購入直後にボタンが機能する、目に見えるアンロックとして審査を支える。

## F. 捨てた案と理由

| 案 | 理由 |
|---|---|
| 初回提出に課金同梱 | A に詳述。SIWA ブロッカー未解消・売り物ゼロの段階で審査変数を増やすだけ |
| Clerk Billing | iOS 3.1.1 不適合（Stripe=外部決済）＋インスタンス共有で影響範囲が検証不能。二重に失格 |
| react-native-iap / expo-in-app-purchases 素実装 | expo-in-app-purchases は非推奨化済み。レシート検証・更新/返金イベント処理の自作が個人開発の運用限界を超える |
| Web外部決済への誘導 | 制度は動いているが、個人開発の初回IAPで規制最前線の解釈リスクを取る意味がない |
| 買い切り（非消耗型）1本 | DB永続保存というランニングコストと収益構造が不一致。広告在庫が育つほど逆ザヤ化 |
| 年額プラン・複数ティア同時展開 | 商品数に比例して審査メタデータ・復元・価格管理が膨らむ。月額1本が付いてから |
| 有料イベント（集まりの参加費） | `drizzle/schema/event.ts` に price/capacity が無く在庫管理から要実装。同ファイル冒頭に doin-challenge.com への移植前提が明記されており有料化は移植性を壊す。資金決済法・特商法・収納代行の論点も個人開発の外。**P3以降も本設計の範囲外** |
| 会議の種（推し専パス / 聖地認定ブースト / すれ違い宝くじ / 実物プリント郵送） | 宝くじは景表法・賭博該当リスクで即死。聖地認定ブーストは「金で地図の真実を曲げる」で DESIGN.md の地図原則違反。推し専パスは推し側の同意設計が未整理。プリント郵送は筋が良いが物流運用が個人開発の外 |
| プレミアム専用の新規訴求バナー・モーダル | 配置禁止マップ（モーダル/インタースティシャル禁止）と訴求密度ルールに抵触。既存カード枠への相乗り（B-2）で足りる |
| スポンサー管理画面 | 直販が1件も取れていない段階でガワだけ作らない |

### H-2. 位置情報アプリ特有の「やってはいけない課金」（恒久禁止リスト）

以下は収益がどれだけ見込めても**実装しない**。ENTITLEMENTS.md の鉄則と同格の禁止事項。

1. **他人の正確な位置・足あとが金で見える**（可視範囲・精度・リアルタイム性の販売）— ストーカー支援。審査以前に人が死ぬ類の設計
2. **「誰が自分の足あと/プロフィールを見たか」の閲覧権販売** — 同上の裏面
3. **すれ違い相手の身元・詳細プロフィールのアンロック販売** — 一方向スタンプ＋X委譲の境界を金で破る
4. **ブロック・通報・位置一時停止・自宅マスク等の安全機能の有料化** — 安全は全員無料。審査でも即死（5.1.1系）
5. **無料側の記録精度・保存期間・チェックイン回数を絞る課金** — 「記録と再訪は課金壁の後ろに置かない」鉄則違反
6. **位置データを使ったターゲティング広告の販売**（生座標・H3セル粒度）— privacy.tsx §4 と既却下案の再確認
7. **すれ違い抽選・ガチャ性のある課金** — 賭博・景表法リスク
8. **金で地図・図鑑の表示順や「聖地」認定を買える仕組み** — 地図＝真実という信頼基盤の破壊（DESIGN.md違反）
