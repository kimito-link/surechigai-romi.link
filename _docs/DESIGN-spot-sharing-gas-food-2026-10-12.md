# 「いいな」スポット共有 設計メモ

- 作成: 2026-10-12 / 改訂: 2026-10-12（ガソリン・ごはんの個別機能から、種類を問わない共有に組み替え）
- 状態: **案（未実装・要判断）**
- 本書は論点整理で、法的助言ではない。未確認の事項は「未確認」と書き、推測で補っていない。

## 0. 決定事項（運営者、2026-10-12）

1. **本題**: ユーザーが「いいな」と思ったものを投稿し、**位置で共有する**。種類は問わない
   （安いガソリン、おすすめのごはん、綺麗な景色、星がきれいに見える場所、聖地、など）。
2. データの出どころは**ユーザー投稿**。X の投稿の取り込みと公開データの利用は、第1段階では使わない。
3. 投稿者は **X のアカウント名を出す**（X のプロフィールへつなぐ）。「使うほど X のフォロワーが増える」という、
   このアプリの根本の考え方に沿う。過去に何度も議論して決めた方針。
4. 最優先は**気軽に投稿できること**。データの有無や入力の多さで、投稿を止めない。
   **ジャンル（タグ）の選択は必須にせず、あとから付けられる**。最小の投稿は、ピンを立てるだけ。
5. 評価（星・点数・順位）は作らない。「人が人に勧める」を核にする。
6. 当初の「ガソリンを先に、ごはんは後に」は、個別機能を前提にしていたため、**この改訂で置き換える**。
   種類は最初から複数で、同じ仕組みの上でタグが違うだけ。

## 1. 何を作るか（一文）

ユーザーが、いいなと思った場所に**ピンを立て**て投稿し（種類のタグと、ひとことは、任意でいつでも添えられる）、
ほかのユーザーが地図でそれを見て、既存の「ここへ向かう」から**そこへ行ける**。

## 2. 既存の設計との違い（方針転換になる点）

`docs/place-info-DESIGN.md`（場所メモ）は、次を**意図して禁止**している。口コミアプリ化して運用が破綻するのを避けるため。

| 場所メモ（現行） | 本書 |
|---|---|
| 自分の足あと1件に添える本人メモ | 場所に紐づく、**他人に見せる**投稿 |
| 他人の足あとに書けない | 他人が見る。投稿は自分の足あとと切り離す |
| 同じ地点のメモを集約しない | 同じ場所の投稿を集約して見せる |
| 検索できない・評価を付けない | 近くの投稿を地図・一覧で見る（評価は付けない） |

つまり本書は、現行設計の一線を**越える**。越える判断は会議で決める（第9節）。
現行の場所メモ（`locations.note`）は、そのまま残す。

## 3. 投稿の形（選択と、任意の短い入力）

| 項目 | 内容 | 備考 |
|---|---|---|
| 位置 | いま居る場所か、地図で選んだ点 | 投稿者の移動履歴とは別物。自宅周辺は投稿できない（第6節） |
| タグ（任意・1〜3個） | 選択式。例: 安いガソリン、おいしいごはん、綺麗な景色、星空、聖地、穴場 | **選ばなくても投稿できる。あとから付けられる**。タグは運営が増やせる。自由入力のタグは置かない |
| 補助項目 | タグに応じて出る任意の数字・選択。例: ガソリンは「価格・油種・確認した日時」 | 必須にしない。気軽さを優先 |
| ひとこと | 任意の短文 | **第1段階では置かない**（置く場合は既存の `moderateText` を通す） |
| 写真 | 任意 | **第1段階では置かない**（写真の位置情報の除去、不適切画像の扱いが要る。第7節） |

評価の星、順位づけ、他人の投稿への返信は作らない。

## 4. 場所の同一性

「同じスタンド・同じ店」を1つにまとめる方式は、2026-10-12 に検索で調べた（一次情報を直接読めていない箇所が多い）。
**景色や星空のスポットは、店舗の公開データに載っていない**。このため、場所は**ピンの座標を主**にする。

### 4-1. 調べた結果（確認できたこと／できなかったこと）

| 候補 | 確認できたこと | 確認できなかったこと |
|---|---|---|
| Overture Maps（Places） | 2023年の初回公開時点で Places は CDLA Permissive 2.0（[Overture の帰属・ライセンス](https://docs.overturemaps.org/attribution)）。日本の件数を約297万件とするのは第三者サービスの主張（[Open Places API](https://openplacesapi.com/coverage/japan)） | 現行版のライセンス、日本の網羅度、スタンド・飲食店の件数と精度 |
| FSQ OS Places | Apache 2.0、商用可、月次更新、帰属表示つき（[Foursquare](https://foursquare.com/?p=44932)、[公式ブログ](https://foursquare.com/resources/blog/data/evolving-fsq-open-source-places/)） | 日本の網羅度、現行の配布条件の詳細 |
| OpenStreetMap（ODbL） | 公開物が「Produced Work」か「派生データベース」かで義務が変わる。派生データベースには同じ条件での公開義務がある（[OSMF のガイドライン](https://osmfoundation.org/wiki/Community_Guidelines/Produced_Work_-_Guideline)）。公開の Nominatim は大量利用を避ける（[利用ポリシー](https://operations.osmfoundation.org/policies/nominatim/)） | ID だけを参照する自前データベースが派生に当たるか |
| Google Places | `place_id` のキャッシュは Places API のポリシーの範囲で許される、と規約に読める。Geocoding 等には「Google 以外の地図との併用禁止」がある（[規約](https://cloud.google.com/archive/maps-platform/terms/maps-service-terms-20260602)） | **Places API に併用禁止があるか**（本アプリは MapLibre を使うため重大） |

日本の公的データ（価格・施設の公開データ）は、今回は調べていない。

### 4-2. 決定した方針

- **ピンの座標を主**にする。アプリ内で場所を作り、自分たちの場所IDを持つ。
- 近くの店・スタンドの**候補**を公開データから出す機能は、あれば便利なだけの**任意の補助**。採用の条件にしない。
  候補に出なければ、そのままピンを立てて投稿できる。
- 同じ場所の投稿の重複は、気軽さを優先して**投稿時には弾かない**。近接した投稿は、表示でまとめる（クラスタ表示）。
  厳密な統合のルール（距離・名前の基準）は、段階1で決める。
- 公開データを候補に使う段階で、各社の規約の原文を読み直し、必要なら弁護士に確認する。

## 5. 鮮度（種類ごとに違う）

- ガソリン価格は数日で変わる。現行の `isPlaceNoteStale` の30日（`modules/encounter/core/place-note.ts`）は長すぎる。
- 景色や星空は、場所そのものの価値は長く続く。ただし「いつ行って見たか」「季節・時間帯」で見え方が変わる。
- したがって、**日数の閾値はタグごとに持つ**（数値は第1段階の計測で決める。ここでは置かない）。
- 古い投稿は薄く表示する。「いつの情報か」は常に画面に出す。自動削除はしない（足あとを消さない方針と整合）。

## 6. プライバシーと安全（既存方針との整合）

- 投稿は**場所に紐づく**。投稿者の座標・足あと・移動履歴とは、画面上でも API でもつなげない。
- 投稿者名は X のアカウント名を出す（決定済み）。ただし、投稿者名が出ると「この人が、この日にこの場所にいた」ことが分かる。
  既知の留意点として、**表示は日付まで（時刻は出さない）**、**投稿はいつでも削除できる**、を設計に入れる。
- **自宅周辺には投稿できない**。既存の `userSettings.homeMaskCell`（自宅セルのマスク）を使う方向で検討する（実装の詳細は未確認）。
- **景色・星空のスポットは、任意の場所にピンを立てられる**ため、店舗よりも次のリスクが大きい（推論）。
  - 私有地・立入禁止区域・危険な場所（崖、道路上、夜間の山中）への誘導
  - 人気が集中した場所の迷惑（駐車、騒音、ごみ）
  - 少数しか知らない場所の特定
  対策の案: 立入禁止・私有地の場所を通報できる、危険な場所向けの注意の定型文（タグごと）、通報が重なったピンの自動非表示。
  いずれも**未実装・要設計**。

## 7. 審査・規制の観点（未確認を含む）

- Apple Guideline 1.2: UGC には、フィルタ、通報と適時の対応、ブロック、連絡先公開が要る。
  現行の `reports`（`locationId`・理由 `inappropriate_place_note`）、`blocks`、`moderateText` は流用できる見込み。
  共有の投稿を通報する経路は**新設が要る**。
- 写真を足す場合は、不適切画像の扱いと、写真に含まれる位置情報（EXIF）の除去が要る。第1段階では置かない。
- **App Store の再審査（4.3(a)、2026-09-23 却下）が通るまで、公開機能は入れない**。作るなら、非公開のまま進める。
- 投稿された場所が、誹謗中傷や、特定の個人・事業者を傷つける内容になる場合の削除請求への対応は、未整備。
- 景品表示法・特定商取引法・各法令の該当性は、**確認していない**。

## 8. 段階導入案

| 段階 | 範囲 | 公開 | 計測 | 止める条件 |
|---|---|---|---|---|
| 0 | 設計の確定、規約・通報の整備、危険な場所への対応方針 | なし | 現行アプリのベースライン | 再審査が通らない |
| 1 | 自分だけが見える形で、タグ付きのピンを残す（現行の場所メモの延長）。重複統合のルールを決める | 非公開 | 投稿率、再訪 | 投稿されない |
| 2 | 選択式のタグ（ガソリン価格などの補助項目を含む）だけを、地域を絞って公開 | 限定 | 投稿数、閲覧、「ここへ向かう」の押下、通報率と処理時間 | 通報の処理が間に合わない、危険な場所の通報が続く |
| 3 | ひとこと・写真・タグの追加を、段階2の運用が回ってから | 限定→全体 | 同上 | 同上 |

数値の目標・停止の閾値は、根拠が無いので置かない。段階0のベースラインを測ってから決める。

## 9. 会議で決めること

1. 現行の「他人の足あとに書けない・集約しない」の一線を、スポット共有のために越えるか。
2. （決定済み）データの出どころはユーザー投稿。立ち上げの密度（近所に情報が無い）の課題への対策
   （最初の地域を絞る、運営が最初の投稿を入れる、など）をどうするか。
3. （決定済み）場所はピンの座標が主。重複の統合ルールを段階1で決める。
4. （決定済み）投稿者名は X のアカウント名を出す。表示は日付まで、削除はいつでも、を設計に入れるか。
5. （決定済み）タグは必須にせず、あとから付けられる。**ジャンルの一覧の中身は、あとで決めてよい**（運営者の方針）。
   決めるときに、タグごとの補助項目と鮮度の考え方を合わせる。
   タグ未設定の投稿を、地図でどう見せるか（共通のピン、鮮度は共通の既定値）は、段階1で決める。
6. 危険な場所・私有地・人気集中への対策（通報、注意の定型文、通報が重なったピンの自動非表示）をどこまで段階2に入れるか。
7. 通報の対応時間の自己設定値（Apple・Google・国内法に具体値は確認できていない）。
8. 再審査が通る前に、どこまで作っておくか（非公開の段階1まで、など）。
9. ひとこと・写真を、段階3で入れるか。
10. 撤退条件の判断者と判断時期。
