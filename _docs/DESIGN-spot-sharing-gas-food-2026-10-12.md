# スポット共有（安いガソリンスタンド・おいしいごはん）設計メモ

- 作成: 2026-10-12 / 状態: **案（未実装・要判断）**
- **決定済み（2026-10-12、運営者）**: データの出どころは**ユーザー投稿**（アプリ内で価格・おいしかったを入力する）。
  X の投稿の取り込みと公開データの利用は、第1段階では使わない。
- **決定済み（2026-10-12、運営者）**: 投稿者は **X のアカウント名を出す**（X のプロフィールへつなぐ）。
  「使うほど X のフォロワーが増える」という、このアプリの根本の考え方に沿う。過去に何度も議論して決めた方針。
- 位置づけ: 既存の「場所メモ」（`docs/place-info-DESIGN.md`）の**次の段階**。本人だけのメモではなく、
  **ほかのユーザーが見て、そこへ行ける**共有にする。
- 前提となる調査: 会議用レポート「ジモティ型掲示の導入判断」（フェーズ2＝粗い粒度のオプトイン公開に当たる）。
- 本書は論点整理で、法的助言ではない。未確認の事項は「未確認」と書き、推測で補っていない。

## 1. 何を作るか（一文）

ガソリンスタンドと飲食店という**固定の場所**に、ユーザーが「価格」「おいしかった」を**決まった項目だけ**で投稿し、
ほかのユーザーが地図で見て、既存の「ここへ向かう」からそこへ行ける。

## 2. 既存の設計との違い（方針転換になる点）

`docs/place-info-DESIGN.md` は、次を**意図して禁止**している。口コミアプリ化して運用が破綻するのを避けるため。

| 場所メモ（現行） | スポット共有（本書） |
|---|---|
| 自分の足あと1件に添える本人メモ | 場所（スタンド・店）に紐づく投稿 |
| 他人の足あとに書けない | 他人が見る。投稿は自分の足あとと切り離す |
| 同じ地点のメモを集約しない | 同じ場所の投稿を集約して見せる |
| 検索できない・評価を付けない | 近くの場所を一覧・並べ替え（ガソリンは安い順） |

つまり本書は、現行設計の一線を**越える**。越える判断は会議で決める（第9節）。
現行の場所メモ（`locations.note`）は、そのまま残す。

## 3. 投稿の項目（自由記述を持たない）

自由記述を置かない理由は、通報・削除の運用負荷を小さくし、Apple Guideline 1.2 の対象範囲を狭めるため（推論）。

### ガソリンスタンド
- 油種（レギュラー／ハイオク／軽油）
- 価格（円/L。数字のみ。上下限を設けて極端な値を弾く）
- 確認した日時（投稿時刻を既定にする）
- 会員価格か現金価格か（任意の選択式）

### ごはん
- 「おいしかった」スタンプ（1人1場所につき1回。取り消し可）
- ジャンル（選択式）、価格帯（選択式）、一人でも入りやすい等のタグ（選択式の少数）
- ひとこと（任意。**第1段階では置かない**。置く場合は既存の `moderateText` を通し、字数は短くする）

評価の星、順位づけ、他人の投稿への返信は作らない。

## 4. 場所の同一性（最大の実装上の論点）

「同じスタンド・同じ店」を1つにまとめる方式。2026-10-12 に検索で調べた（一次情報を直接読めていない箇所が多い）。

### 4-1. 調べた結果（確認できたこと／できなかったこと）

| 候補 | 確認できたこと | 確認できなかったこと |
|---|---|---|
| Overture Maps（Places） | 2023年の初回公開時点で Places は CDLA Permissive 2.0（[Overture の帰属・ライセンス](https://docs.overturemaps.org/attribution)）。地図や図表に文字の帰属表示やロゴを必須としない旨を FAQ が述べる、と検索要約にある。日本の件数を約297万件とするのは第三者サービスの主張（[Open Places API](https://openplacesapi.com/coverage/japan)） | **現行版のライセンス**、日本の網羅度、日本の `gas_station` や飲食店の件数と精度。上流データ（Meta・Microsoft 等）固有の帰属義務の有無 |
| FSQ OS Places（Foursquare の公開データ） | Apache 2.0、商用可、月次更新、帰属表示つき（[Foursquare](https://foursquare.com/?p=44932)、[公式ブログ](https://foursquare.com/resources/blog/data/evolving-fsq-open-source-places/)）。後の版は、アクセストークン付きの配布方式に移ったと書かれている | **日本の網羅度**、現行の配布条件の詳細 |
| Foursquare Places API | 非商用の小規模は無料枠、商用は有料と報じられている。公式の開発者規約に無料クレジットの記載あり（[規約](https://foursquare.com/legal/terms/developermasterterms/)） | 料金の現行値、`fsq_id` の長期保存の可否 |
| OpenStreetMap（ODbL） | 公開物が「Produced Work」か「派生データベース」かで義務が変わる。派生データベースには同じ条件で公開する義務（share-alike）がある（[OSMF のガイドライン](https://osmfoundation.org/wiki/Community_Guidelines/Produced_Work_-_Guideline)）。公開の Nominatim は大量利用を避け、キャッシュとプロキシを置くよう求める。1秒1リクエストの上限は第三者の写しで確認、オートコンプリート不可は二次情報（[Nominatim 利用ポリシー](https://operations.osmfoundation.org/policies/nominatim/)） | OSM の ID だけを参照する自前のデータベースが、派生データベースに当たるか |
| Google Places | `place_id` のキャッシュは、Places API のポリシーの範囲で許される、と規約に読める。Geocoding などの API には「Google 以外の地図との併用禁止」がある（[Google Maps Platform の規約](https://cloud.google.com/archive/maps-platform/terms/maps-service-terms-20260602)） | **Places API に同じ併用禁止があるか**（本アプリは MapLibre を使うため、重大）。他のデータのキャッシュ期間 |

日本での公的データ（国や業界団体の価格・施設データ）は、**今回は調べていない**。

### 4-2. 方式の比較

| 案 | 内容 | 評価（推論を含む） |
|---|---|---|
| A. 外部の場所IDに紐づける | Overture／FSQ OS／OSM 等の ID に投稿を結びつける | 日本の網羅度が未確認。ODbL の share-alike、上流データの帰属、データ更新に追随する運用が要る |
| B. アプリ内で場所を作る | 自分たちの場所IDを持ち、ユーザーの座標と名前から作る | 規約の制約が少なく、データを自分で持てる。ただし同じ店の重複が起きる |
| B+. アプリ内の場所IDを主にし、公開データは「候補の提示」に使う | 投稿時に、近くの場所の候補を公開データから出し、ユーザーが選ぶ。選んだら自分の場所IDに結びつける | 重複を減らせる。公開データの許諾は、候補表示に必要な範囲だけで済む（要確認） |
| C. 近接で自動統合 | 一定距離内を同一とみなす | 隣接する店・スタンドの取り違えが起きる。単独では不適 |

### 4-3. 決定（運営者、2026-10-12）: B+ を採る。最優先は「ユーザーが気軽に投稿できること」

- **採用: B+**（アプリ内の場所IDを主にし、公開データは候補の提示に使う）。
- **原則: 投稿を、データの有無で止めない。** 公開データに日本の店が揃っているかは、採用の条件にしない。
  候補に出なければ、ユーザーが場所をその場で作って、そのまま投稿できる。
- 投稿の流れ（最短）: スタンドや店の近くで開く → 近くの候補が出る（あれば）→ 選ぶ（無ければ名前を入れて作る）→
  価格かスタンプを入れて送信。入力は、選択と数字だけで済ませる。
- 同じ場所の重複は、投稿のしやすさを優先して**あとから統合する**（同じ距離内・同じ名前の候補を運営側で束ねる）。
  投稿の時点で厳しく弾かない。
- 公開データ（Overture／FSQ OS）の日本での網羅度の実測は、**採用の判断には使わない**。候補の質を上げる改善として、
  必要になったときに行う。
- 場所を作れることによる乱用（実在しない場所、嫌がらせの名前）は、既存の通報と `moderateText` で扱う。
  詳細は第7節。
- ライセンス・規約は、候補に公開データを使う段階で、一次情報（各社の規約原文）を読んで確認する。必要なら弁護士に確認する。

## 5. 鮮度（ガソリン価格は特に重要）

- 現行の `isPlaceNoteStale` は30日で「古い」とする（`modules/encounter/core/place-note.ts`）。ガソリン価格には長すぎる。
  共有では、**日数の閾値を種類ごとに持つ**（目安は第1段階の計測で決める。ここでは数値を置かない）。
- 古い投稿は薄く表示し、さらに古いものは並べ替え・一覧から外す。**「いつの情報か」は常に画面に出す**。
- 価格は「最新の投稿が正」とは限らない。外れ値や、会員価格との混在を、表示でどう扱うかは未決。

## 6. プライバシー（既存方針との整合）

- 投稿は**場所に紐づく**。投稿者の座標・足あと・移動履歴とは、画面上でも API でもつなげない。
- 投稿者名は出すか（X のアカウント名）、出さないか。X で名前を出す前提のアプリだが、**投稿者名の公開は会議で決める**。
- 自宅・職場周辺の場所に投稿が集中すると、居住地の推測につながりうる。第1段階は、**営業している店舗・スタンドに限る**。
- 位置情報の再特定の研究（Strava のプライバシーゾーンが破られた例）は、レポートに記載のとおり。

## 7. 審査・規制の観点（未確認を含む）

- Apple Guideline 1.2: UGC には、フィルタ、通報と適時の対応、ブロック、連絡先公開が要る。
  現行の `reports`（`locationId`・理由 `inappropriate_place_note`）、`blocks`、`moderateText` は流用できる見込み。
  共有の投稿を通報する経路は**新設が要る**。
- **App Store の再審査（4.3(a)、2026-09-23 却下）が通るまで、公開機能は入れない**。作るなら非公開のまま進める。
- 価格の誤り・古さによる苦情への扱い（免責の表示、規約）は未整備。
- 飲食店の投稿は、名誉・信用に関わる投稿（誹謗中傷）の削除請求の対象になりうる。ガソリンより運用が重い（推論）。
- 景品表示法・特定商取引法の該当性は、**確認していない**。

## 8. 段階導入案

| 段階 | 範囲 | 公開 | 計測 | 止める条件 |
|---|---|---|---|---|
| 0 | 設計の確定、場所の同一性の方式決め、規約・通報の整備 | なし | 現行アプリのベースライン | 再審査が通らない |
| 1 | 自分だけが見える形で、価格・おいしかったを記録（現行の場所メモの項目化） | 非公開 | 記録率、再訪 | 記録されない |
| 2 | ガソリンだけ公開。投稿は少数の地域・利用者で試す | 限定 | 投稿数、閲覧、「ここへ向かう」の押下 | 通報の処理が間に合わない、古い価格の苦情 |

数値の目標・停止の閾値は、根拠が無いので置かない。段階0のベースラインを測ってから決める。

## 9. 会議で決めること

1. 現行の「他人の足あとに書けない・集約しない」の一線を、スポット共有のために越えるか。
2. （決定済み）データの出どころは**ユーザー投稿**。X の投稿の取り込み、公開データの利用は、
   API の料金・権限・利用許諾が未確認のため、必要になったときに別途調べる。
   ユーザー投稿は、最初は近所に情報が無い（立ち上げの密度）という課題がある。段階2で地域を絞って試す理由の一つ。
3. （決定済み）場所の同一性は B+。最優先は気軽に投稿できること。重複の統合ルール（距離・名前の基準）を、段階1で決める。
4. （決定済み）投稿者名は X のアカウント名を出す。上記の留意点（日付まで、削除可）を設計に入れるかを確認する。
5. ガソリンとごはんを同時に始めるか、ガソリンだけで先に試すか（運用負荷はごはんの方が重い、という見立て）。
6. 通報の対応時間の自己設定値（Apple・Google・国内法に具体値は確認できていない）。
7. 再審査が通る前に、どこまで作っておくか（非公開の段階1まで、など）。
